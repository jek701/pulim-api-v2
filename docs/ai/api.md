Verify before commit: `npm run typecheck && npm test && npm run build`.

Modes: `MAINTENANCE_MODE=true` (503 except /health), `BACKGROUND_JOBS_ENABLED=false`, `NOTIFICATIONS_ENABLED=false`, `NOTIFY_EMBEDDED`.

## Storage: "document store on MySQL" (CRITICAL)
Firestore→MySQL cutover done **2026-10-13 ~23:52 Tashkent** (`docs/mysql-cutover.ru.md`, `docs/mysql-migration-progress.ru.md`), 3242 docs / 28 collections, 0 mismatches.
Firestore source frozen & kept for recovery; **no runtime Firestore use**. Firebase Auth still used (same uids).
Every entity table has the same generic schema: `id VARBINARY(2048)` (old doc id), `data_json JSON`, `types_json JSON` (type sidecar: timestamp, int64, …),
plus **projection columns** auto-filled from data_json (user_id, household_id, card_id, category_id, linked_transaction_id, chat_id, username, status, created_at_ms, updated_at_ms, date_ms, run_at_ms, next_attempt_at_ms, lease_until_ms, scheduled_at_ms, next_daily_at_ms, family_household_id, expires_at_ms) and the same 9 indexes.
Extra: relational `push_devices` (unique normalized APNs token, owner uid, per-device sandbox/production, app metadata and disable state; migration `004_push_devices`, owner applies separately), capture tables (migration `005_capture`, see Capture), `schema_migrations`, `migration_*`, `legacy_documents`, `household_members` (mirror of memberIds).
- Queries: `queryTable/filterQuery/orderQuery/limitQuery/afterQuery/countQuery` → `readDocument`. Ops `== < <= > >= in array-contains`, evaluated on `JSON_EXTRACT` with **strict JSON type guard** (Firestore semantics). Ordering by a field excludes docs lacking it.
- **Unsigned-timestamp gotcha (fixed in 3887c5c):** MySQL may report epoch-ms as `JSON_TYPE='UNSIGNED INTEGER'`; numeric guard must include `'INTEGER','UNSIGNED INTEGER','DOUBLE'` (`src/db/documents.ts:160`). Before the fix notifications never planned/delivered.
- `runSqlTransaction(work)`: REPEATABLE READ, UTC, reads `FOR UPDATE`, writes buffered; **all reads before first write** (else "Read all records before scheduling writes"); retried up to 5× on deadlock → **no external side effects inside**.
- `patch` dotted keys = field paths; `save({merge:true})` dotted keys literal. `patchValue.delete/increment/arrayUnion/arrayRemove` emulate FieldValue.
- No SQL FKs; relations live in JSON. Business timestamps = epoch ms numbers. No TTL cleanup job for `expires_at_ms` (retention undecided).
- Adding a queryable field = add a projection in `db/documents.ts` (affects all tables). Don't add relational columns/joins casually.

Key tables (`src/db/tables.ts`, 40): profiles (id = uid; Telegram users `tg_<telegramId>`), user_settings, categories (defaults `${uid}__default__${type}_${slug}`), subcategories,
cards, transactions (Telegram ids `telegram_<sha>`), budgets (`${uid}_${categoryId}`), savings_goals, debts, deposits, subscriptions, planned_expenses,
households, household_invites (7-day token), household_invite_picks, telegram_users, telegram_login_requests (bot login, 5-min, hashes only), phone_verifications (HMAC of code), shortcut_tokens (sha256), billing_events, fx_rates,
ai_chats, ai_usage, ai_feedback, ai_forecast_cache, telegram_updates/operations/drafts/sessions/messages/usage, notifications, notification_tasks/state/stats,
communication_campaigns, in_app_messages, communication_deliveries, dev_notes, dev_note_screenshots.

## Auth
All `/v1/*`: `Authorization: Bearer <Firebase ID token>` → `req.uid`. Ownership via `readOwned`/`userScopedRepo` (403 wrong owner, 404 missing).
- **Telegram Mini App** `POST /auth/telegram {telegramInitData, chatId, language?, firebaseIdToken?}`: HMAC check with bot token (Ed25519 fallback); creates `tg_<id>` account + profile + default categories or resolves mapping; custom claims `{provider:'telegram', telegramId}`; returns customToken. With firebaseIdToken = link to existing account.
- **Native app via bot deep link** `POST /auth/telegram/login-request` → `t.me/<bot>?start=login_<nonce>` → bot `/start login_…` approves (same `signInTelegramUser` as the Mini App) → app polls `POST /auth/telegram/login-request/:requestId/exchange {deviceSecret}` for a one-time customToken. Contract: [docs/telegram-bot-login.md](../telegram-bot-login.md).
- **Phone (Eskiz SMS)** `POST /auth/phone/send-code`, `/auth/phone/verify`: +998 only, 6-digit code, HMAC with `PHONE_CODE_PEPPER`, TTL/cooldown/attempt limits; `purpose:'link'` attaches phone to current uid. Replaced Firebase phone auth.
- Email/Google/Apple: native Firebase client; API only records metadata on `POST /v1/profile/bootstrap`.
- Owner-only: `DEV_NOTES_UIDS` gates dev notes + communications admin (others get 404). `NOTIFY_ALLOWED_UIDS` = notification rollout allowlist.
- Machine: billing HMAC, Telegram `X-Telegram-Bot-Api-Secret-Token`, Shortcut personal key.

## Money invariants
- **Single balance rule** `domain/balance.ts balanceDelta(cardType, txType, amount)`: credit card `balance` = debt used (expense adds); debit/cash = real money.
- Balances are **stored**, never recomputed from history. Every money op is one `runSqlTransaction` (tx row + balance together).
- System ops carry `source` ∈ transfer, return, debt_payment, savings, deposit_interest, deposit_close, deposit_replenish, deposit_withdraw, subscription (+ `sourceLabel`, categoryId usually ''). Generic PATCH rejects them → use dedicated endpoints. Stats ignore transfers.
- Transfer = one tx (`type:'expense'`, cardId, toCardId, toAmount, toCurrency), two balance moves; cross-currency needs toAmount.
- Return = income row with `linkedTransactionId`, increments original `returnedAmount`; only expenses; capped; same currency; deleting original deletes refunds.
- FX: `baseAmount`, `fxRate`, `fxRateSource` (NBU|manual); rates from cbu.uz (called "NBU" in code), cached in `fx_rates`, refreshed 6 h. Currencies UZS, USD, EUR, RUB, GBP, CNY, KZT, TRY, AED, JPY.
- Deleting a card/debt/deposit does NOT reverse related transactions.

Trial: explicit `POST /v1/profile/trial/start`, once, 7 days, `source:'trial'`; blocked after any paid history.

Never replay the old DEAD trial event in payment outbox; never roll back payment DB with app DB.

## Telegram bot & quick entry (`src/telegram/`, spec `docs/TZ-telegram-quick-entry.md`)
Webhook → dedupe in `telegram_updates` → 200 immediately → async processing with lease; recovery every 30 s, abandon after 10 attempts.
Commands `/start`, `/help`, `/language` (`/lang`, `/til`), `/cancel`, `/stop`, hidden owner-only `/idea`.
Text → quotas (10/min, 20/day free, 100/day Premium) → **LLM parse** (`TELEGRAM_PARSE_MODEL` default `gpt-5.4-mini`, escalation `gpt-5.6-terra` on low confidence; items transaction/transfer/debt/debt_payment, ≤10)
→ deterministic resolvers (amount k/m, date Asia/Tashkent, category, card) → save immediately via idempotent `create*Once` (marker in `telegram_operations`) or **draft** with reasons (`telegram_drafts`; drafts never affect balances). `FX_UNAVAILABLE` → `waiting_fx` retried up to 168 h.
Telegram tx get `origin:'telegram'` (never `source`). Callback data `v1:<action>:<item>:<option>` ≤64 bytes (indexes into `telegram_messages`).
Non-transaction text → stateless AI answer (counts AI quota). Premium media: voice (`gpt-4o-mini-transcribe`, ≤60 s), receipt photo (vision model). Per-user switch `profile.telegramQuickEntryEnabled`.

## Notifications (Telegram + native APNs, dark launch / owner-only rollout)
Telegram-only users retain the daily digest, Telegram buttons and existing reminders, events, timing and quiet hours. When APNs is configured and a user has enabled devices, individual push messages replace Telegram; `alsoTelegram:true` retains Telegram copies. Notification types without a push template (including trial_started and already-queued daily rows) keep going to Telegram regardless of alsoTelegram. Missing APNs env, an unreadable key or the device migration falls back to Telegram. The reminder master switch, `NOTIFICATIONS_ENABLED` and `NOTIFY_ALLOWED_UIDS` remain authoritative; `PUSH_ENABLED` defaults false. Campaigns retain their existing exemption from the reminder master switch and their own marketing consent: push requires marketing.inApp; Telegram requires marketing.telegram. A device suppresses campaign Telegram only when push marketing is permitted. Legacy campaign external counters retain their `telegram*` field names and include routed push deliveries.

Native device registry is relational `push_devices`, separate from the JSON entity tables and sync feed. Owner applies additive `004_push_devices`; no runtime auto-migration. Capability `pushNotifications` is true only with PUSH_ENABLED, configured APNs credentials and a readable key (probed once at startup), and an available push_devices table (cached probe on first use). Restart after installing the table/key to refresh cached readiness. Registration and profile metadata update share one SQL transaction. A token can move to another uid; an old owner's DELETE cannot delete it. APNs retirement compares lastSeenAt so a delayed response does not disable a fresh registration. Token-bearing DELETE URLs are redacted from API request logs.

`SqlTransaction.flush` derives goal-reached, family-joined, optional family-expense and paid-Premium-activated transitions only for recipients with an enabled device, and saves durable notification rows on the same executor before the effect commits. Outbox ids use duplicate-safe INSERT first, avoiding locking pre-reads of absent keys; budget tasks are inserted before locking/updating their debounce state. Non-lock hook errors are logged and swallowed so user writes succeed; lock/deadlock errors propagate to the transaction retry. Storage/migration imports do not load application env; boot injects the hook switch. Failed/retried transactions never send. After commit the API kicks delivery using the same SQL claim as the worker. Device owners get per-user/category budget tasks in the effect transaction, debounce 25 seconds, and skip the legacy per-user task. Telegram-only users retain `NOTIFY_BUDGET_DEBOUNCE_MS` (default 300000ms). New task docs expire after 90 days like notification docs. The 5-second delivery cycle also processes due budget tasks, independent of the 15-minute planner. Threshold keys remain once per category/local month.

The planner pages enabled-device owners even when they have no Telegram chat. It prequeues individual reminders for today/tomorrow at local 10:00 (subscription, debt 3-day/due/weekly overdue, credit card 2-day, deposit 7-day/interest day, goal 7-day, trial 3/1-day, Premium expiry, Monday/first-of-month summaries) and 21:00 (no-entry evening prompt, first 14 local calendar days). Planned expenses are excluded because the app schedules them locally. Registration and committed reminder/profile changes also trigger a coalesced per-user planning pass, including language/timezone updates, without waiting for the periodic scan. It refreshes current data before sending, skips paid/deleted/inapplicable reminders, and adjusts unattempted slots after timezone changes. Monthly summaries take precedence over weekly summaries, and reports over the evening prompt; habit messages have a shared once/day reservation. Current model has no credit-card minimum-payment amount or subscription account reference: credit reminders omit the amount and subscription account uses a localized generic label. Weekly reports omit a missing top-category clause; uz/en month names are capitalized in monthly titles, while Russian retains lowercase genitive.

Delivery: minute-precision custom quiet hours in profile timezone (default Tashkent) for device owners; Telegram-only users retain the original NOTIFY_QUIET_* window/timezone. Only APNs budget_100 and apple_billing_failed bypass silence; Telegram always defers, including copies/fallback after urgent push. Maximum six logical notifications/user/local day. First accepted channel atomically counts the notification; device and Telegram acknowledgements prevent resending successful recipients on a sibling retry. A shared lease prevents concurrent API/worker claims. Unknown-outcome expired leases remain failed (existing conservative at-most-once policy); an unacknowledged reservation can reduce available slots until midnight. A process crash between remote acceptance and local acknowledgement cannot provide distributed exactly-once guarantees.

APNs uses ES256 JWT (50-minute cache), persistent unref'ed HTTP/2 sessions per sandbox/production host, alert headers, expiration and hashed budget collapse ids. Invalid tokens and BadTopic/TopicDisallowed/DeviceTokenNotForTopic retire the affected device with a reason, permitting same-job Telegram fallback. Provider-auth 403 pauses until token refresh without burning attempts; topic errors do not open that circuit. 429/5xx use bounded backoff; Telegram 429 retains 0–1000ms jitter. Both API and worker close APNs on shutdown; API delivery/planning kicks drain for up to five seconds. All 21 approved push texts exist in uz/ru/en, with 50-character titles and 150-character bodies. Payloads follow the native contract (`type`, expo-router `link`, optional `entityId`, `notificationId`, category and interruption level). Links keep the plural contract paths; the app maps them to its current singular detail screens. Apple billing failure has a template/type only; no IAP source is connected.

Delivery retains notify.sent/skipped/blocked/failed/safety_cap logs. APNs attempts use separate `apns:<hour>` notification_stats docs; the existing Telegram forbidden-rate alert uses only Telegram attempts. Each APNs attempt also logs event→enqueue→send→response durations plus rolling per-type p50/p95 (last 500 samples/process), without token or content. Config: `PUSH_ENABLED`, `APNS_KEY_ID`, `APNS_TEAM_ID`, `APNS_KEY_PATH`, `APNS_BUNDLE_ID` (default `com.izik.pulim`, enforced at registration). Key readability is probed once; credentials are read only by the runtime sender when configured. Enabling notifications and applying the production migration remain owner-controlled operations. See [task 3 report](../next/task3-api-report.md) and [notification spec](../TZ-notifications.md).

## Capture: voice and receipt scan (branch `claude/capture`, dark until the owner applies `005_capture`)
Contract (shared with the native app): "Shared contract" of `docs/next/task4-capture.md` in the pulim-react-native repo (branch `claude/capture`); implementation report [task 4 API report](../next/task4-api-report.md). Code: `src/capture/`, `src/routes/capture.routes.ts`, CLI `src/cli/merchants.ts`, `src/cli/captureEval.ts`.
- **Capability:** `GET /v1/sync/capabilities` → `capture: { voice, receipt }`, both true only with `OPENAI_API_KEY` and the applied `005_capture` marker (`isCaptureStorageReady`: positive probe cached until restart, a missing one re-probed every 30 s). Every `/v1/capture/*` route is 503 `capture_unavailable` when dark and 401 for anonymous Firebase users.
- **Endpoints** (errors are flat `{ code, message, error:{code,message}, quota? }`): `GET /quota` → `{ used, limit, resetsAt, premium }`; `POST /voice` multipart `audio` (m4a/aac, ≤ 3 MB, ≤ 60 s + 2 s tolerance, checked from the container) + optional `language` `uz|ru|en`, `timezone` → `{ transcript, drafts, quota }`; `POST /receipt/soliq` JSON `{ url, timezone? }` → `{ receipt, drafts, duplicateOf?, quota }`; `POST /receipt/photo` multipart `image` (JPEG, long side ≤ 2000 px, ≤ 3 MB) + optional `timezone` → same. Uploads are parsed with busboy in memory only (never on disk). Nothing is saved by these calls. 402 `capture_quota_exceeded` carries `quota`; 502 `soliq_unavailable` (the app then offers the photo path); 422 `not_a_receipt`; 502 `capture_unavailable` for provider failures (generic, no provider text). Per-user rate limits: 20/min voice and photo, 10/min Soliq.
- **Quota:** `capture_usage (uid, month, count)`, month = calendar month in Tashkent (UTC+5, no DST). Limit 5 free / 300 Premium (`getIsPremium`). Voice and photo count; Soliq does not unless `CAPTURE_COUNT_SOLIQ=true`. Reserved atomically (`UPDATE … WHERE count < limit`) before any model call, refunded when the work fails or a voice note yields no operation.
- **Amounts are code, not model:** `capture/amounts.ts` is a deterministic ru/uz(Latn+Cyrl)/en parser ("25 минг", "1,2 млн", "полтора миллиона", "yigirma besh ming", "$20", "100 баксов"). The model returns `amountSpan` (exact transcript substring) and intent; the final number always comes from the parser applied to words actually spoken. Disagreement, a bare small number ("обед 45", scale not spoken), a paraphrased span, or an ambiguous span → `lowConfidenceFields` has `amount`. Photo receipts: item/total arithmetic sanity check instead.
- **Voice pipeline** (`models.ts`, `service.ts`): transcription `CAPTURE_TRANSCRIBE_MODEL` (default `TELEGRAM_TRANSCRIBE_MODEL`) with a hint of category and recent merchant names; parse `CAPTURE_PARSE_MODEL` (default `TELEGRAM_PARSE_MODEL`) via Responses API, `store:false`, hand-written strict JSON schema. Model context: user categories + aliases (`telegram/categoryAliases.ts`), accounts, last ≤ 30 personal `comment → category` pairs, today in the user's timezone. Several operations per phrase. Unsure category → `categoryId: null` + low; account only when named (`accountMentioned`), otherwise null and *not* flagged (the app pre-fills its default). Only token counts/latency go to `ai_usage` (features `capture_voice|capture_parse|capture_receipt|capture_category`); never transcripts, receipts or audio.
- **Soliq** (`capture/soliq.ts`, shape verified by the lead against two real receipts): POST `https://new-ofd.soliq.uz/api/payment` (`/payment/mobile-dashboard` for the `h` variant) with `X-Timestamp` in **Unix seconds** (milliseconds get 401) and `X-Signature` = hex HMAC-SHA256(`terminalId:paymentNo:seconds`) keyed by `SOLIQ_OFD_SIGNING_KEY` (public-bundle constant, env only). Response `{ success, message, status, data }`; `paymentDate` is `DD.MM.YYYY HH:mm:ss` Tashkent time; money is in sum (`SOLIQ_AMOUNT_DIVISOR` stays 1); TINs are JSON numbers. Items: `amount` = quantity (may be fractional), `goodPrice` = unit price, `price` = line total before discount, `discount`; contract item = `quantity=amount, price=goodPrice, discount, amount=price-discount`. Seller = `extraInfo.merchantTin` → most common `comitentTin` → `tin`; name `extraInfo.companyName`, address `extraInfo.address`. Σ(price−discount) ≠ total → `amount` in `lowConfidenceFields` (no error). `isRefund: 1` or `refundPaymentId` → `receipt.isRefund: true` and an **income** draft with `categoryId: null` and `category` flagged. 10 s timeout, one retry, 30-day cache in `capture_receipt_cache` by receiptKey (allowlisted fields only), log `capture.soliq_failed {statusCode}`. **Only `extraInfo.companyName/merchantTin/address` are read from `extraInfo`; every other key (phone, card numbers, taxi trips, flight passport/PINFL, cadastral and account numbers, coordinates, …) is never read into the result, cache or logs** (test fills all of them). `extraInfo.fiscalSign` is used only inside the dedupe hash so the `s` and `h` QR variants share one receiptKey.
- **Category inference order** (`capture/categories.ts`): (1) the user's own choice for this TIN (`merchant_user_category`), (2) `verified` merchant or consensus (≥ 3 distinct voters and ≥ 70% weight), (3) IKPU prefix map weighted by item amount (longest prefix; unknown 5-digit classes are classified once by the model and stored), (4) model guess, stored as a 0.25-weight `ai` vote with no voter, returned only as a **low-confidence** suggestion of the user's own category, (5) null + low. A standard key maps back to the user's category only if they have that default category (`standardCategoryKey`: stable seeded id, else the Telegram resolver's name+icon+type test). Personal categories never vote globally.
- **Learning on save:** `POST /transactions` accepts optional `capture { kind, receiptKey?, merchantTin?, suggestedCategoryId?, draftId? }`. The schema is lenient on purpose (bad fields dropped, unknown keys stripped, bad `kind` drops the object) so it can never fail a money write; PATCH and household create ignore it. It is stored on the transaction; `capture_receipt_key` (virtual generated column + `capture_owner_receipt` index on the `transactions` table) powers `duplicateOf { date, transactionId }`. After commit (`tx.afterCommit`, never on replays/rollbacks) `learnCommittedCapture` upserts `merchant_user_category`, bumps `merchants.seen_count/last_seen` and casts one vote (double when the user changed the suggestion). Shared vote rows carry only `HMAC(CAPTURE_VOTER_SALT, uid)` in `merchant_latest_votes`; without a ≥ 16 char salt nobody votes globally. Failures are swallowed and logged as `capture.learning_failed`.
- **Tables (all additive, `005_capture`):** `merchants`, `merchant_category_votes` (aggregated, no uid), `merchant_latest_votes` (salted hash per voter), `merchant_user_category` (per user), `ikpu_category_map` (seeded in `capture/seeds.ts`), `capture_usage`, `capture_receipt_cache`, `capture_learning` (idempotency), `capture_owner_summary` (weekly claim by owner hash), plus the `transactions.capture_receipt_key` projection. `src/db/migrate.ts` stays self-contained (`capture/migration.ts` imports no env). The owner applies the prod migration separately.
- **Owner tools:** `npm run merchants -- review` (new and contested, JSON), `npm run merchants -- verify <tin> <standardKey>` (on the server: `node dist/cli/merchants.js …`). The worker sends a short Telegram digest to `DEV_NOTES_UIDS` on Monday 10:00 Tashkent (merchants first seen in 7 days or with disagreeing voters), claimed once per week and owner.
- **Evaluation:** `tests/capture/eval/phrases.json` (146 synthetic phrases: ru, uz Latin, uz Cyrillic, en, mixed, multi-operation). `npm test` scores the parser on the whole set (≥ 98% required; currently 100%). `npm run capture:eval` is opt-in (needs `OPENAI_API_KEY`, makes real calls, skipped otherwise) and prints accuracy per field and language for the parse stage.
- **Env:** `CAPTURE_TRANSCRIBE_MODEL`, `CAPTURE_PARSE_MODEL`, `CAPTURE_RECEIPT_MODEL`, `CAPTURE_COUNT_SOLIQ`, `CAPTURE_VOTER_SALT`, `SOLIQ_OFD_SIGNING_KEY`, `SOLIQ_AMOUNT_DIVISOR` (placeholders in `.env.example`).

## Offline sync (additive, contract v1) — full contract: [docs/offline-sync.md](../offline-sync.md)
For the native app (SQLite + outbox). Branch `claude/api-offline-sync-f3399a`; needs **migration `003_offline_sync` applied by the owner before it is active** (code is safe without it: `isSyncEnabled()` false → no change index, no idempotency markers, `/v1/sync/changes` 503, everything else as before).
- **Choke point:** every document write goes through `SqlTransaction.flush` (`db/documents.ts`). It records one row per changed doc in `sync_entries` (upsert or tombstone, per-user scope `u:<uid>` from `data.userId`; profile/settings by doc id; household-owned rows excluded) and allocates `seq` from `sync_state` **last in the transaction** (counter row lock held to commit ⇒ seq follows commit order, no timestamp overlap windows). Do not write entity tables outside `documents.ts`. `updatedAt` is NOT relied on for sync.
- **Idempotency:** `middleware/idempotency.ts` (after `authenticate`) + AsyncLocalStorage context (`db/idempotencyContext.ts`). Only routes in the `HONOURED` allowlist (single-transaction mutations) honour the key, all others ignore it (`Idempotency-Ignored: true`) — add new single-tx mutations there. `runSqlTransaction` plain-INSERTs the marker (`idempotency_keys`, id sha256(`uid:key`)) before the first effect flush, so marker + effect commit atomically; a duplicate key (`ER_DUP_ENTRY`) aborts the transaction (`IdempotencyConflict`) and the error handler replays the stored response. Final 2xx response is stored before it is sent (`res.json`/`res.end` wrapper). Errors are never stored. Because services open their own transactions, **never run non-idempotent side effects before the effect transaction inside a mutating handler**.
- **Client ids:** optional `id` on create schemas (`domain/clientId.ts`); create-or-get inside the same tx; PATCH/household schemas must not accept `id`.
- Endpoints: `GET /v1/sync/capabilities`, `GET /v1/sync/changes?cursor&limit`. Maintenance (`db/syncMaintenance.ts`, in the API process): prune tombstones > 90 d (sets `floor_seq` ⇒ 410 `CURSOR_EXPIRED`) and expired idempotency markers.
- Env: `OFFLINE_SYNC_ENABLED` (kill switch), `SYNC_EPOCH`. Tests: `npm run test:mysql` (`tests/migration/offline-sync.integration.test.ts`), unit tests in `tests/sync`, `tests/clientId`.

## Gotchas / known issues (2026-10-21)
- `PATCH /v1/cards/:id` accepts `cardType` and `balance` without free-plan checks (free user can switch debit→credit or overwrite balance); `enforceLimit` counts only personal cards; household budgets/goals not Premium-gated.
- Telegram initData verification has **no `auth_date` freshness check**.
- Planner with `NOTIFY_ALLOWED_UIDS` reads `document.data.notifications` before checking `exists` → allowlisted uid without profile aborts the tick.
- No pagination anywhere; `userScopedRepo` sorts in memory.
- No TTL cleanup for drafts, markers, notifications, phone codes, invites.
- Firestore leftovers: `firebase.json`, `firestore.indexes.json`, firestore dep, `uid` duplicate in telegram_users, stale comments/docs.
- README omits many endpoints and points to a non-existent CLI header comment.
- **Secrets:** local secret files (`.env*`, `serviceAccountKey.json`, `oldServiceAccountKey.json`, `.migration-artifacts/` with real data snapshots) are gitignored and must never be printed or committed.
